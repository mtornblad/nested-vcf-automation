# Modular nested VCF blueprints

This is an experimental, separately packaged variant of **Full Stack VCF**.
VCF Operations Orchestrator collects one lab plan and requests four catalog
items in order. The existing blueprint remains in the repository root.

The implementation starts from automation commit
`b6bca4c4dafc935a72f93effda1d2c9b0ebd83f6`. The image IDs, bootstrap key names,
NVMe controller layout, Windows routes, and DNS configuration follow that
revision. The source contract is recorded in
[contracts/source.json](contracts/source.json).

## Ownership and order

| Catalog item | Owns | Receives from Foundation |
| --- | --- | --- |
| Nested VCF Modular - Foundation | Namespace, VPC, external IP, NAT, subnets, trunk bindings, VyOS and its bootstrap Secret | Nothing |
| Nested VCF Modular - ESXi | Variable number of ESXi VMs, optional NVMe capacity PVCs, bootstrap Secret | Existing namespace name |
| Nested VCF Modular - Installer | Installer VM, bootstrap Secret, optional existing VCF custom resources | Namespace name and external IP |
| Nested VCF Modular - Jumphost | Windows VM and bootstrap Secret | Existing namespace name |

Only Foundation creates the namespace. Each later blueprint declares an
`existing: true` namespace reference and resolves its own CCI context. Each
deployment owns a distinct Secret. There are no references to resources inside
another blueprint's expression scope.

The first workflow runs sequentially: Foundation, then selected ESXi,
Installer, and Jumphost stages. Foundation creates the complete DNS data for
the planned lab before the other appliances are requested. Optional stages
can be deselected in the vRO form.

## Shared request contract

[lab.schema.json](contracts/lab.schema.json) describes `nested-vcf.modular/v1`.
[lab-plan.example.json](contracts/lab-plan.example.json) contains a complete
public example. The vRO `LabPlan` class generates this object from the form;
all selected stages receive the same object.

| Input | Used by | Purpose |
| --- | --- | --- |
| `lab` | All | Public placement, image, host, network, DNS, NTP and VCF settings |
| `lab_password` | All | Plaintext disposable-lab credential, no default |
| `vyos_rest_api_key` | Foundation | Plaintext router API key, no default |
| `namespace_name` | ESXi, Installer, Jumphost | Actual namespace returned by Foundation |
| `external_ip` | Installer | Foundation's external NAT address |
| `vcf_spec_json` | Installer | JSON generated by the vRO `VcfSpec` class |
| `run_vcf_installation` | Installer | Invoke the existing bring-up custom resources; default `false` |
| `depot_url` | Installer | Required by the vRO workflow when bring-up is enabled |

Foundation outputs `contract_version`, `lab_name`, `namespace_name`,
`vpc_name`, `external_ip`, and `vyos_ip`. The workflow verifies the contract,
lab name, project, and catalog item before using those outputs. Retain the
blueprint names and output keys when editing a deployment variant.

The public plan contains no passwords or API key. Bootstrap Secrets, catalog
requests and the generated VCF specification carry the supplied plaintext
credentials, matching the requested lab model. Generated specifications are
runtime artifacts and must not be added to this repository.

## Build, publish and download

Use Java 17, Maven 3.9+, Python 3.11+ and the existing private Maven profile for
Build Tools 4.25.0. From this `modular/` directory:

```bash
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -r requirements.txt
make test
make package
make push PROFILE=lab
```

`package` writes the Maven package under `target/`. `push` builds and uploads
the objects selected in this directory's `content.yaml`. Release the four
blueprints and expose them through the intended VCFA All Apps catalog/project.
Uploading source alone does not establish catalog entitlement.

From the umbrella root, the equivalent entry points are:

```bash
./orchestration/run_automation.py test --variant modular
./orchestration/run_automation.py build --variant modular
./orchestration/run_automation.py upload --variant modular --profile lab
```

To export edits made in Automation, commit or stash component changes, then:

```bash
make pull PROFILE=lab
# Or, from the umbrella root:
./orchestration/run_automation.py download --variant modular
```

Pull selects this variant's content descriptor. It refuses to overwrite a
dirty component unless explicitly forced. Review the diff and run `make test`
after exporting. These commands do not select the root Full Stack VCF package.

## Network and guest behavior

The current form supports /24 networks inside a private /16. The vRO plan
allocates host addresses, VLANs and pools once and shares them across all
four requests. It rejects collisions between ESXi hosts, Installer, VCF
appliances and the VCF address pools. Host count changes drive VM count,
PVC count, DNS records and JSON `hostSpecs` together.

The modular defaults retain the source revision's nested MTU of **8800**;
the generated DVS MTU is 100 bytes higher, capped at 9000. The form permits
1600–9000 for an environment with a verified underlying transport. This input
does not configure the outer NSX transport or physical network.

VyOS resolves through its own DNS service at `127.0.0.1`, forwards external
queries to the selected upstream server, and serves the lab's forward and
reverse records. The external VIS record remains
`vis-appliance.dclab.se -> 10.114.10.9`. Installer and the new SDDC Manager
have separate names and addresses. Installer and Jumphost PTR records follow
their selected host addresses.

The tested vApp keys are retained for each image. In particular, ESXi keeps
its `guestinfo.*` keys, VyOS keeps `enable_ssh`, `enable_rest` and
`config_base64`, and Installer keeps its mixed key set. Do not normalize these
keys merely because the packages are now separate.

The ESXi disk option retains the source image's NVMe controllers 0 and 1,
with the extra capacity disk attached on controller 1. Disk size and HCL
auto-claim are separate options. Image availability, nested virtualization in
the VM class, namespace quota and the outer network still require a platform
check.

## VCF JSON and optional bring-up

The Orchestrator component constructs a JavaScript object and serializes it
with `JSON.stringify`. This avoids string-template comma and password-escaping
errors. The Installer blueprint receives the resulting string instead of
generating a second specification. Save the `vcfDeploymentJson` workflow
output and validate it using the shared validator in the repository root:

```bash
python3 ../scripts/validate_vcf_spec.py /path/to/vcf-deployment.json
```

The package includes the existing `VCF` and `VCF Installler Certificate`
custom-resource definitions, with their existing identities. Their referenced
vRO workflows must already exist and be accessible in the target environment.
Those workflow implementations are now included as native XML/JavaScript in
the [Orchestrator package](https://github.com/mtornblad/nested-vcf-orchestrator/blob/main/docs/custom-resources.md).
Publish that package before uploading the custom-resource definitions. The
Configurator certificate-delete library workflow remains an external dependency.
The `Custom.vcf` create descriptor includes `sddcSpec` to match the exported
Create VCF workflow input. The definitions are shared with Full Stack VCF; review any changes
to them as changes affecting both variants.

For the first test, leave **Run VCF bring-up** off. A successful VCFA deployment
and the CCI `VirtualMachineCreated` condition establish provisioning, not guest
bootstrap or DNS/API readiness. Check VyOS, ESXi and Installer before importing
the JSON or enabling the existing bring-up integration on a later test.

## Lifecycle and verification

Delete child deployments before Foundation: Jumphost, Installer, ESXi, then
Foundation. Keep Foundation's lease at least as long as its children. VCFA
cannot infer this cross-deployment ownership from an existing namespace
reference. The vRO workflow retains successful deployments on failure and
returns IDs for inspection/resume; it does not automatically roll back a lab.

Offline checks validate YAML uniqueness, input schemas, resource references,
ownership boundaries, guest property keys, DNS, host counts, optional disks,
and the bring-up switch. They do not execute VCFA expressions or contact
Supervisor. The first catalog request is the integration test for those layers.
